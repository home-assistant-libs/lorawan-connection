---
title: Build a device library
description: Organize device models into a library with a public collection, a CLI, and tests.
---

A device library gives applications Python objects for the devices it supports.
Its public entry point is a collection that accepts a `Connection`. Applications
discover devices through that collection, read their attributes, subscribe to
updates, and call their command methods.

Keep payload decoding, measurement units, and command encoding in this package.
The application supplies the connection and decides how to display the data.
Release and test the library independently of the applications that use it.

Start with a model from [Devices and collections](/lorawan-connection/modelling/overview/).
That guide covers decoding, state, commands, and model lifecycle. This page shows
how those pieces fit into a Python package.

## Organize the package

Add `lorawan-connection` as a dependency in your package's `pyproject.toml`.
Use a `devices/` folder with one file per model, such as `devices/s2101.py`.
Keep each model and its decoder together. For a SenseCAP library, the layout could be:

```text
pyproject.toml
sensecap_lorawan/
  __init__.py       # collection and public exports
  __main__.py       # command-line entry point
  devices/
    __init__.py
    s2101.py        # S2101 model and decoder
tests/
  conftest.py       # collection fixture
  devices/
    test_s2101.py
```

The [quickstart example](/lorawan-connection/getting-started/quickstart/#example-library)
contains the S2101 model and decoder. Put those in `devices/s2101.py`.
Move decoders shared by several models into a separate module.

## Expose a collection

Define the collection in `__init__.py`, alongside the public model exports:

```python
from lorawan_connection import DeviceCollection

from .devices.s2101 import S2101


class SenseCapDeviceCollection(DeviceCollection[S2101]):
    DEVICES = (S2101,)


__all__ = ["S2101", "SenseCapDeviceCollection"]
```

The collection is the application's entry point for all supported devices on a
network. It creates models, routes their events, and reports additions and
removals. A device-added callback receives a model ready for the application to
observe.

This gives callers stable imports as the package grows. With several device
classes, use their union as the collection's type parameter and list them all
in `DEVICES`. Move the collection to `collection.py` if it grows substantial
custom logic, and keep exporting it from `__init__.py`.

## Keep the application boundary clear

The library owns payload formats, ports, units, device commands, and reported
state. Its public attributes and methods let applications use devices without
interpreting LoRaWAN messages.

The application owns credentials, connection setup, and reconnection. Keep backend
imports in connection scripts such as the CLI. The device models use the shared
event and downlink interfaces. See [Connecting to ChirpStack](/lorawan-connection/connection/chirpstack/)
for a complete application using the SenseCAP collection.

For example, an application with an open connection can monitor the library like
this. Cancel `monitor()` to stop; its `finally` block closes the collection.

```python
import asyncio

from lorawan_connection import Connection
from sensecap_lorawan import S2101, SenseCapDeviceCollection


async def monitor(connection: Connection) -> None:
    devices = SenseCapDeviceCollection(connection)

    def device_added(device: S2101) -> None:
        def show_readings() -> None:
            print(device.descriptor.name, device.temperature, device.humidity)

        show_readings()
        device.add_update_listener(show_readings)
        device.add_remove_listener(
            lambda: print("Removed:", device.descriptor.name)
        )

    devices.subscribe_device_added(device_added)
    try:
        await devices.async_setup()
        await asyncio.Event().wait()
    finally:
        devices.close()
```

The collection creates a model for each supported device and attaches its command
sender. Values can be `None` until the first report. A model can expose several
measurements, channels, or sub-systems; one event can update any number of them.

Closing the collection clears its models' listeners and leaves the supplied
connection open. Device removal calls the model's removal listeners. Closing the
collection during application shutdown does not report every device as removed.

## Add a CLI and tests

Expose a command with the [command-line helper](/lorawan-connection/patterns/cli/).
It accepts the collection's model classes, connects to a server, and prints device
updates. This lets users try the library with their devices.

Use the [testing guide](/lorawan-connection/patterns/testing/) to create a collection
fixture with a device already added. Test the library through its public model
attributes, command methods, and update listeners using captured payloads.
